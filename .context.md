## Purpose
**MCO1 SokoBot** — an academic AI course project (DLSU CSINTSY "Intsy" major course
output). The task: implement an AI search algorithm that solves **Sokoban** puzzles
within a 15-second thinking limit. A Java starter framework (GUI, file reader, driver)
is provided and **frozen**; the only code we are allowed to write/modify lives in the
`solver` package. The bot receives a level and must return a playable move string
(`u`/`d`/`l`/`r`) that pushes every crate onto a target. Hidden grading levels are
expected to have ~2–8 crates; target is solving ≥80% of them.

## Tech Stack
- **Language/runtime:** Java (plain `javac` / `java`, no build tool). Standard JDK only.
- **GUI:** Java Swing (`gui` package) — renders the board and animates the solution.
- **No external libraries.** Spec allows standard collections + data-structure libs,
  but **forbids any external AI/search-algorithm library.**
- **Platform:** developed on Windows (PowerShell test script), but `.sh` launchers exist too.

## How to Build / Run / Test
Run everything **from `release/sokobot/`** (the launchers `cd`-assume this; `FileReader`
loads `maps/<name>.txt` and `GamePanel` loads `src/graphics/*.png` via relative paths).

- **Bot mode (GUI):** `.\sokobot.bat <mapname>` → compiles, runs `main.Driver <map> bot`.
  Press SPACE in the window to start the solver, then watch the animated solution.
- **Free play (GUI):** `.\freeplay.bat <mapname>` → play manually with arrow keys.
- **Batch evaluation (headless-ish):** `.\run_tests.ps1` → compiles, runs every map in
  `check` mode, prints a Map/Status/Time/Moves table and a pass count. Each run writes
  `temp.txt` (`<time> PASS|FAIL <moves>`) which the script parses, then `System.exit(1)`.
- **Single-map timing harness:** compile & run `solver.TestProfile`
  (`javac -cp src src/solver/TestProfile.java; java -cp src solver.TestProfile`).
  ⚠ It hardcodes map `original1` but its log messages still say `original2` (stale).
- **Manual:** `javac -cp src src/main/Driver.java` then
  `java -cp src main.Driver <map> <fp|bot|check>`.
- `<mapname>` = a file in `maps/` without `.txt` (e.g. `original1`, `threeboxes2`).

## Architecture
Packages under `release/sokobot/src/`:
- **`main`** — `Driver.main(mapName, mode)`: reads the map, builds the `GameFrame`,
  and dispatches to `fp` (free play), `bot` (GUI solve), or `check` (auto-solve + write
  `temp.txt` for scripted testing). *(provided, do not modify)*
- **`reader`** — `FileReader.readFile(name)` loads `maps/<name>.txt` into a `MapData`
  (`tiles[][]`, `rows`, `columns`). Fixed 100×100 buffer. *(provided)*
- **`gui`** — `GameFrame` + `GamePanel` (Swing rendering, input, animation, the
  **15-second** timeout) and `BotThread` (runs the solver on a background thread so the
  EDT can time it). *(provided)*
- **`solver`** — **OUR CODE.** `SokoBot.solveSokobanPuzzle(...)` is the graded entry point.

**Primary flow:** `Driver` → `GameFrame`/`GamePanel.startThinking()` copies the board
and spawns `BotThread` → `BotThread.run()` calls `SokoBot.solveSokobanPuzzle(width,
height, mapData, itemsData)` → returns a move string → `GamePanel.playSolution()`
animates it move-by-move, updating `progress`/`moves`. In `check` mode the result is
written to `temp.txt` and the JVM exits.

**Map encoding (important):** `mapData` holds only **static** tiles (`#` wall, `.`
target, ` ` floor). `itemsData` holds **movable** items (`@` player, `$` crate, ` `).
A crate/player on a target shows as `$`/`@` in `itemsData` while the `.` stays in
`mapData`. Note `width = columns`, `height = rows`.

## Core Concepts & Domain Logic (all in `SokoBot.java`)
- **Cell encoding:** every cell is an int `r*width + c` (`encode`/`row`/`col`). State =
  player cell + a **sorted** `int[]` of crate cells.
- **Search:** **weighted A\*** over *crate pushes* (macro moves), not individual player
  steps. Frontier is a `PriorityQueue<Node>`; `Node.priority = pushes + heuristic * 3`
  (weight 3 ⇒ greedy-ish, **inadmissible**, faster but solutions may be non-optimal in
  move count). `g` = number of pushes.
- **Per-state reachability:** `computeReachability(player, crates)` BFS finds all floor
  cells the player can walk to without crossing a crate, **and records the walk path
  string** to each cell. A push of crate `i` in direction `d` is legal only if the
  player can reach the cell behind the crate and the destination cell is free. The walk
  path + the push letter are appended to build the exact final move string.
- **Heuristic:** minimum-cost assignment of crates→targets via **bitmask subset DP**
  (`heuristic`), using precomputed BFS `targetDistances` (per target, distance to every
  floor cell, ignoring crates). Returns `INF` if any crate cannot reach any target —
  this `INF` check is currently the **only active deadlock filter** (prunes
  unreachable/dead-square placements softly).
- **Symmetry/dedup:** `getRepresentativePlayer` = lowest-index reachable cell; states are
  keyed by `(representative player, crates)` so player-equivalent positions collapse.
  `bestCost` (HashMap<String,Integer>) stores best push-count per state key.
- **Precompute (`initializeTargets`):** target set, per-target distance maps,
  `deadSquares` (pull-reachability liveness), and `masksByBitCount` (subset lists grouped
  by popcount for the DP).
- **Time guard:** `TIME_LIMIT_NANOS = 14.5s`; the main loop checks `timedOut()` and bails,
  staying under the GUI's 15s (`SOLUTION_TIME_LIMIT = 15000` in `GamePanel`).

## Conventions & Patterns
- 2-space indentation, `solver` package, plain Java, no annotations beyond `@Override`.
- Heavy use of flat `int[]`/`boolean[]` indexed by encoded cell for speed (avoid object
  allocation in the hot loop) — match this style for new solver code.
- Directions are the parallel arrays `DR/DC/MOVE` indexed `0=u,1=d,2=l,3=r`.
- Keep all new logic inside `solver`; never touch `main`/`gui`/`reader` (graded constraint).
- The entry signature **must remain** `public String solveSokobanPuzzle(int width,
  int height, char[][] mapData, char[][] itemsData)`.

## Gotchas & Constraints
- **Visited-set keying is subtle (was a bug — now fixed).** Two maps are in play:
  `bestCost` keyed by the *actual* `(player, crates)` for insert-time dedup, and `closed`
  keyed by the *canonical* `(representativePlayer, crates)` written only at expansion. They
  must stay separate — the original code shared one map for both, so nodes whose player sat
  on the region representative self-skipped (`g >= g`) before expansion and the search
  exhausted early, returning `""` on solvable maps. Don't re-merge them.
- **Deadlock pruning is now ON:** `isDeadSquare` (dead-square / simple deadlock) and
  `has2x2Deadlock` (frozen 2x2 block) are active and sound. `hasComponentDeadlock` remains
  available but **disabled** (`if (false && ...)`) — it's the more aggressive/risky one; a
  false positive there would re-introduce the "returns empty on solvable maps" failure, so
  only enable it with careful re-testing against all sample maps.
- **Exponential heuristic:** the assignment DP and `masksByBitCount` are `O(2^T · T)` in
  target count `T`, and allocate `2^T` arrays each call. Fine for ≤~12 targets (2–8 crate
  spec range), but will blow up memory/time for large target counts.
- **Weighted A\* is inadmissible** (weight 3): solutions are found fast but may use more
  moves than optimal. Acceptable for this project (grading rewards solving, not optimality)
  but don't claim optimality in the report.
- **String-based state keys** (`key()`) and **string move accumulation** in every `Node`
  are simple but allocation-heavy; a bottleneck if puzzles get large. Packing crates into
  a `long`/byte key would be the optimization if needed.
- Runtime artifacts/build output are committed: `temp.txt` (stale `0.08 PASS 37`) and all
  `*.class` files. Launchers `del /s /q *.class` then recompile, so committed `.class`
  files are noise.
- `FileReader` uses a fixed 100×100 char buffer and pads with spaces — maps must fit.
